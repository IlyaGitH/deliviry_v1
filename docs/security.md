# Защита доступа к АТСД

Рабочая схема: **браузер → HTTPS с клиентским сертификатом → nginx → Unix-сокет → веб-сервер → локальный ROS 2 → мост VEX**. Камера и WebSocket проходят через тот же шлюз. Снаружи доступен порт 443; веб больше не слушает 8080/8090. Wi-Fi, автоматическое подключение к известным сетям и SSH оператора этот установщик не перенастраивает.

Это реализация защиты сетевого интерфейса и локальных данных. Она **не является подтверждением полного соответствия регламенту**: выбранная сигнализация по лидару не измеряет открытие крышки, не блокирует движение; Secure Boot, защита от администратора root и физическая блокировка всех свободных разъёмов не реализованы. Эти ограничения нельзя устранить одной настройкой HTTPS.

## Обновление существующего Pi

Обновляйте стоящего робота по SSH. При первом обновлении Pi нужен интернет для пакетов `nginx`, `python3-cryptography` и `nftables`. Проверка зависимостей выполняется до остановки служб. Пароли и ключи генерируются на Pi; исходники менять не требуется.

```bash
(
  set -e
  cd ~/atsd_ws
  saved_stash=""
  if ! git diff --quiet || ! git diff --cached --quiet; then
    git stash push -m "Pi перед обновлением $(date +%Y%m%d-%H%M%S)"
    saved_stash=$(git rev-parse refs/stash)
  fi
  git pull --ff-only origin main
  if [ -n "$saved_stash" ]; then
    git stash apply "$saved_stash"
  fi
  sudo bash src/atsd_bringup/scripts/update.sh
  sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py export "$(id -un)"
)
```

При конфликте Git блок останавливается до установки: копия изменений остаётся в stash. Установка не обходит конфликт и не стирает локальные настройки. Прошивка VEX в этом обновлении не меняется.

Первый экспорт создаёт `~/atsd-access`. Повторный экспорт создаёт отдельный каталог с суффиксом и печатает его путь. Внутри:

| Файл | Назначение |
|---|---|
| `atsd-ca.crt` | Корневой сертификат именно вашего робота |
| `android.p12`, `ios.p12`, `ubuntu.p12` | Разные клиентские сертификаты и закрытые ключи |
| `android-password.txt`, `ios-password.txt`, `ubuntu-password.txt` | Пароли импорта соответствующего P12 |
| `admin-password.txt` | Отдельный пароль администратора веб-интерфейса |
| `README.txt` | Адрес и отпечаток корневого сертификата |

На доверенном Ubuntu-компьютере скопируйте пакет:

```bash
scp -r ilya@rasber.local:~/atsd-access ./
```

Пакет содержит закрытые ключи. Его нельзя класть в открытое облако конкурса или Git. На телефон передавайте только CA, его P12 и пароль импорта, например по USB. Пароль администратора передавайте только оператору. Каждому отдельному телефону нужен отдельный сертификат; предустановленные `android`, `ios`, `ubuntu` рассчитаны на три устройства, а не на всех пользователей одной ОС.

## Установка доступа в браузерах

**Android / Chrome / Яндекс Браузер.** В настройках безопасности телефона найдите установку сертификатов (обычно «Шифрование и учётные данные → Установить сертификат»). Установите `atsd-ca.crt` как сертификат центра сертификации, а `android.p12` — как сертификат VPN и приложений, не Wi-Fi. Введите пароль из `android-password.txt`. Откройте `https://rasber.local/`; в раздаче Pi можно `https://10.42.0.1/`. При запросе выберите сертификат `ATSD android`. Названия разделов зависят от производителя Android; телефон может потребовать включённую блокировку экрана.

**iOS / Safari, Chrome, Яндекс Браузер.** Откройте `atsd-ca.crt`, установите загруженный профиль через «Настройки → Основные → VPN и управление устройством». Затем «Основные → Об этом устройстве → Доверие сертификатам» — включите полное доверие этому CA. Установите `ios.p12` как отдельный профиль, введя `ios-password.txt`. Откройте тот же HTTPS-адрес, при запросе выберите `ATSD ios`. Сначала проверьте Safari. Ограничения импорта и выбора клиентских сертификатов могут отличаться между версиями iOS и браузерами; реальные телефоны в облачной проверке не участвовали.

**Ubuntu / Chrome, Яндекс Браузер.** Через управление сертификатами браузера импортируйте CA в доверенные центры, а `ubuntu.p12` в личные сертификаты. Для браузеров, использующих пользовательскую базу NSS, можно выполнить на компьютере оператора (не на Pi):

```bash
sudo apt-get install -y libnss3-tools
mkdir -p "$HOME/.pki/nssdb"
if [ ! -f "$HOME/.pki/nssdb/cert9.db" ]; then
  certutil -N -d "sql:$HOME/.pki/nssdb" --empty-password
fi
certutil -A -d "sql:$HOME/.pki/nssdb" -n ATSD-robot-CA -t 'C,,' \
  -i "$HOME/atsd-access/atsd-ca.crt"
pk12util -i "$HOME/atsd-access/ubuntu.p12" -d "sql:$HOME/.pki/nssdb" \
  -w "$HOME/atsd-access/ubuntu-password.txt"
```

Полностью закройте и снова откройте браузер. Если он использует собственное хранилище, импортируйте эти же файлы через его настройки. Не обходите ошибку имени сертификата: используйте `rasber.local` или адрес AP `10.42.0.1`. Текущий LAN IPv4 добавляется в сертификат при установке; новый адрес DHCP после установки может не совпасть с ним. Имя остаётся предпочтительным.

Отпечаток CA можно сверить через уже доверенный SSH:

```bash
openssl x509 -in /etc/atsd/security/ca.crt -noout -fingerprint -sha256
```

CA действует 10 лет, клиентские сертификаты — 1 год. Серверный сертификат обновляется при установке. Для продления клиентского сертификата отзовите старый и выдайте новый.

## Роли и работа с заказами

* Администратор: сертификат устройства и пароль из `admin-password.txt`; создаёт заказ, меняет точки, задаёт позицию, отменяет/продолжает рейс, видит камеру и общий журнал.
* Отправитель/получатель: сертификат устройства и персональная ссылка, которую администратор получает при создании заказа. Открытие отсека и подтверждение доступны только для своего заказа и соответствующего этапа. Пароль вводить не нужно: нажмите кнопку входа по полной ссылке. Если ссылка обрезана, запросите новую у администратора. В том же браузере вход меняет текущий сеанс администратора на роль клиента; для возврата откройте `/login` и введите пароль администратора.
* `?role=admin` не даёт прав. Роль хранится на сервере в сеансе. Ссылка привязывается к первому успешно вошедшему клиентскому сертификату; чужой сертификат с той же ссылкой не допускается.
* Секрет ссылки находится после `#`, не передаётся nginx в URL и сразу удаляется из адресной строки страницей входа. На диске остаётся только его SHA-256. Срок входа по ссылке — 48 часов от выдачи ссылки незавершённого заказа; сеанс — 12 часов, либо до выхода/перезапуска веба/отзыва доступа.
* Потеряли ссылку или заменили телефон: администратор нажимает **«Заменить ссылки доступа»** у активного заказа. Старые ссылки и сеансы клиентов аннулируются, привязка снимается. Движение и этап доставки не меняются.
* Камера теперь находится по `https://rasber.local/debug/`, только для администратора. Клиенты не получают сырые изображения, диагностическую консоль и общий журнал заказов.

Чтобы добавить ещё одно устройство на Pi:

```bash
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py add-client phone2
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py export "$(id -un)"
```

Чтобы отозвать потерянное устройство:

```bash
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py revoke phone2
```

Обе операции перезапускают веб для немедленного прекращения существующих сеансов. Повторно войдите на оставшихся устройствах. Отзыв проверяется сервером приложения, поэтому даже ранее выданный сертификат CA больше не даёт доступа к страницам. CA и сертификаты других устройств сохраняются.

## Какие механизмы работают

| Угроза | Реализация |
|---|---|
| Прослушивание Wi-Fi, подмена веб-сервера | TLS 1.2/1.3, доверенный локальный CA, проверка имени сервера |
| Незарегистрированное устройство | Обязательный клиентский сертификат TLS и список разрешённых сертификатов на сервере |
| Подмена роли/заказа | Проверка прав на каждом HTTP-запросе, фильтрация WebSocket, повторная проверка сеанса при каждой отправке |
| Подбор пароля | Scrypt с индивидуальной солью; ограничение неудачных попыток по сертификату |
| Повтор перехваченной команды | Одноразовый билет на 30 с, привязанный к сертификату, методу, точному URL и SHA-256 тела; атомарное погашение SQLite; сброс после рестарта |
| Подмена тела команды | Билет становится непригоден при изменении хотя бы одного байта тела или URL |
| Межсайтовая отправка | SameSite Strict / Secure / HttpOnly cookie, проверка Origin, обязательный нестандартный заголовок; CORS не включён |
| Вставка HTML/скриптов | Динамические строки выводятся как текст; CSP запрещает внешние/встроенные скрипты, фреймы и `eval` |
| Подмена исходников служебным пользователем | Исходники и установленный код принадлежат root; подписанный Ed25519 манифест; проверка перед запуском шести ROS-служб |
| Перезапись журнала пользователем `atsd` | Отдельный root-процесс, интерфейс только добавления через Unix-сокет; HMAC-цепочка и отдельная контрольная запись |
| Утечка данных заказа с диска | `orders.json` шифруется Fernet; секреты доступа хранятся только как хеши; исходный ключ не в Git |
| Накопление сырых изображений/лидара | Штатный поток обрабатывается в RAM. Известные старые rosbag в `/opt/atsd/lidar-check-*` автоматически шифруются AES-256-GCM при установке |

Код не блокирует открытие замка по заряду или напряжению. Временное отключение света при открытии сохраняется. Ограничение CPU удалено; обновление восстанавливает прежний предел и удаляет старую службу.

Служба `atsd-audit` пишет события входа/отказа, принятые команды и результат, импульс замка и выбранные события робота. Перед сетевой командой запись должна быть подтверждена журналом — иначе команда не выполняется. Если журнал отказал после действия, ответ честно сообщает, что результат не подтверждён: не повторяйте команду вслепую. События ROS повторно отправляются из очереди до восстановления журнала; очередь в RAM ограничена 1024 событиями и не переживает выключение питания. Переполнение выводится как ошибка, а не выдаётся за гарантированную доставку.

Журнал ограничен 50 МБ, после достижения предела новые команды отклоняются. Его не удаляют и не ротируют молча. Проверка цепочки:

```bash
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-audit.py verify
sudo tail -20 /var/lib/atsd-security/audit.jsonl
```

Контроль целостности выполняется перед стартом, не непрерывно. Он обнаруживает изменения после установки, но **не удостоверяет происхождение скачанного Git-коммита**. Установщик root осознанно подписывает текущую установленную сборку. Он не заменяет Secure Boot и не защищает от root, подмены ОС/SD-карты либо физического доступа к цепям привода.

## Задняя сигнализация по лидару

`rear_guard_node` использует `/scan` в `laser_frame` и свежую `/drive/odom`. Область относительно лидара: от 0 до **55 см назад**, **20 см вправо и влево**. Два или более конечных отражения внутри области должны непрерывно присутствовать не менее **1 секунды**, пока скорость больше 0,03 м/с или угловая скорость больше 0,05 рад/с. Пропуск сканов больше 0,45 с, потеря одометрии или исчезновение объекта сбрасывают подтверждение. `inf` и `NaN` не являются объектом.

После подтверждения публикуется `SECURITY_REAR_INTRUSION`, зумер включается на 2 с, сообщение появляется в журнале веба и передаётся в защищённый журнал. Повторное срабатывание возможно после исчезновения объекта. Статус доступен в `/security/rear_status`: `idle`, `watching`, `alert`, `unavailable`.

**Узел не публикует команды движения, паузы или аварийной остановки.** Общая защита от столкновений продолжает независимо обрабатывать тот же лидар. Она может остановить робот по своей причине; этот модуль её не отключает.

Это сигнализация об объекте в заднем габарите, не доказательство взлома. Объект вне плоскости лидара, открытая крышка без отражения или вмешательство на стоянке не обнаруживаются этим правилом. Пункт регламента «датчик вскрытия → блокировка задания» этой согласованной реализацией не закрывается.

## Хранение и доверенные границы

Закрытые ключи CA, подписи и журнала находятся в `/var/lib/atsd-security` (root, 0700); конфигурация веба — `/etc/atsd/security/web.json` (root:atsd, 0640). Пользователь `atsd` доверен в части обработки заказа и ROS. Захват этого пользователя, root либо физического VEX находится вне защиты браузерной аутентификации. Для ROS выбран только интерфейс loopback CycloneDDS. Отдельная таблица nftables блокирует входящий извне UDP в диапазоне DDS домена 17 (11650–11899); правила SSH/HTTPS/Wi-Fi и чужие таблицы firewall не меняются. При отказе установки этих правил ROS-службы не запускаются. Локальный ROS не аутентифицирует процессы доверенного компьютера; USB-протокол Pi–VEX не получил криптографическую аутентификацию. Неиспользуемый serial-getty отключён, права USB-последовательных устройств ограничены группой dialout; все свободные физические USB-разъёмы автоматически не отключаются, чтобы не нарушить позднее подключение VEX и датчиков.

Потеря браузера не равна потере сервера заказов: сервер работает на самом Pi. Закрытие вкладки не прекращает автономный рейс. Существующие watchdog привода и проверки свежести датчиков сохраняются. В защищённой установке веб-процесс отправляет подтверждение работоспособности каждые 0,5 с из своего цикла обработки HTTP. Мост принимает только свежие подтверждения с монотонной меткой времени. Через 3 с без них мост прекращает heartbeat VEX; существующий watchdog прошивки через 0,5 с ставит автономное движение на паузу связи. Новые подтверждения восстанавливают heartbeat; остальные причины остановки сохраняются. Это контроль процесса сервера, не доступности браузера, Wi-Fi или TLS-шлюза. События ORDER_SERVER_LOST/OK и причина паузы выводятся пользователю, когда связь с вебом доступна. Проверка включается по умолчанию при наличии установленной конфигурации безопасности; исходная установка без неё не требует запущенного веба.

Штатно сырые сенсорные записи не создаются. Произвольные ранее сделанные копии на других путях установщик не может гарантированно найти. Не включайте постоянный `ros2 bag record` на SD-карту для демонстрации. Ранее записанные `lidar-check-*` сохраняются зашифрованными; восстановление выбранного файла выполняется в RAM и удаляется перезагрузкой:

```bash
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py decrypt-recording \
  /opt/atsd/lidar-check-20261112-132719/lidar-check-20261112-132719_0.mcap.encrypted
```

В команде нужен существующий путь вашего архива. После проверки GCM файл появится в `/run/atsd-recordings`; повреждённый архив не выдаётся как готовый файл. Не теряйте root-конфигурацию ключей: без неё старые данные не расшифровать. Шифрование существующего файла не гарантирует физического стирания старых блоков на SD-карте.

## Проверка после установки

```bash
systemctl is-active atsd-ros-network atsd-audit atsd-web atsd-gateway atsd-sensors atsd-actuators
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-security.py verify
sudo /usr/bin/python3 -I /usr/local/libexec/atsd-audit.py verify
sudo journalctl -b -u atsd-audit -u atsd-web -u atsd-gateway --no-pager -n 60
sudo nft list table inet atsd_ros
sudo ss -ltnp | grep -E ':(443|8080|8090)[[:space:]]'
timeout 10s sudo -u atsd /opt/atsd/run.sh ros2 topic echo /security/rear_status
```

Ожидается HTTPS 443 и отсутствие TCP-слушателей веба на 8080/8090. Без клиентского сертификата даже страница входа недоступна. У отправителя попытка открыть `/debug/` или чужой заказ должна отклоняться. На проверке сигнализации нужно обеспечить реальные свежие одометрию и сканы: одно сообщение в ROS не доказывает работоспособность на корпусе.

В облаке проверяются политика доступа, replay/подмена тела/CSRF, связь cookie с сертификатом, отзыв ссылок, шифрование и повреждение архива, подмена манифеста и журнала, геометрия и выдержка задней сигнализации. Интеграционная проверка использует настоящий nginx/TLS и Chromium с клиентским сертификатом. Проверка ROS/systemd на конкретном Pi, физических отражений, зумера и импорта сертификатов на ваших телефонах остаётся аппаратной приёмкой после установки; облачные тесты её не заменяют.

Повторяемая проверка TLS и трёх ролей находится в `tools/security_browser_check.py`. Она запускается обычным пользователем на компьютере разработки с nginx, Chromium, Python-пакетами playwright/cryptography/fastapi/uvicorn/numpy/pydantic и websockets; создаёт временный CA и имитацию робота, удаляет тестовые ключи после завершения. Пути к программам можно задать через `ATSD_TEST_NGINX` и `ATSD_TEST_CHROMIUM`. В браузерной части проверяется клиентский сертификат, а доверие серверному CA и имя проверяются отдельно curl без отключения проверки TLS. Скрипт использует локальный порт 18443.
